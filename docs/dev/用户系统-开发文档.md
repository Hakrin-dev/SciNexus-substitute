## 1. 总体架构

```
┌─────────────────────────────┐
│ Next.js 前端 (本仓库)         │
│  stores/auth.ts  ── 登录态    │
│  components/auth/  ── 弹窗    │
│  app/reset-password/ ── 找回  │
│  app/settings/     ── 设置页  │
└──────────────┬──────────────┘
               │ REST /api/v1,Authorization: Bearer <access_token>
┌──────────────▼──────────────┐
│ 用户服务                      │
│  auth(登录/注册/验证码/token) │
│  profile(资料/账号/关联)      │
│  preference(语言/外观/通知)   │
└──────────────┬──────────────┘
        ┌──────▼──────┐  ┌────▼─────┐  ┌──────▼──────┐
        │ PostgreSQL  │  │ Redis    │  │ 短信/邮件网关 │
        │ users 等表   │  │ 验证码/  │  │              │
        │             │  │ 频控/锁定 │  │              │
        └─────────────┘  └──────────┘  └──────────────┘
```

### 1.1 鉴权机制(Token)

- 登录/注册成功签发 **双 token**:
  - `access_token`:JWT,有效期 **2 小时**,前端内存持有 + 请求头 `Authorization: Bearer`;
  - `refresh_token`:不透明随机串(≥256 bit),有效期 **30 天**,HttpOnly + Secure + SameSite=Lax Cookie,路径限定 `/api/v1/auth`;
- 滑动续期:access_token 过期后前端调 `POST /auth/refresh`(带 Cookie)换新对;refresh_token 每次使用后轮换,旧值作废(重用旧值视为泄露,吊销该用户全部会话);
- 登出/改密/重置密码:服务端将 refresh_token 加入吊销表(Redis,TTL = 剩余有效期),该用户所有 token 失效;
- 前端 401 统一处理:先尝试 refresh 一次,仍 401 则清空登录态(见 §5.3)。

## 3. API 规范

### 3.1 通用约定

- 请求/响应均为 JSON,`Content-Type: application/json`;
- 成功:`{ "code": 0, "data": {...} }`;
- 失败:`{ "code": <业务码>, "message": "<面向用户的文案>" }`,HTTP 状态码同步语义(400/401/403/404/429/500);
- 业务码段位:`1xxxx` 用户系统(见 §6);
- 所有写接口幂等键:验证码发送、注册等携带 `Idempotency-Key` 头,服务端 5 分钟内去重。

### 3.2 验证码 `POST /auth/verification-codes`(公开)

请求:

```json
{ "account": "user@example.com", "scene": "login" }
```

- `account`:邮箱或 `1[3-9]\d{9}` 手机号;
- `scene`:`login | register | reset_password | change_account`;
- 行为:
  - `register` 时 account 已注册 → `10003`;
  - `reset_password` 时不做账号存在性区分(防枚举),统一返回成功;真实不存在的账号发送后验证码无法通过校验;
  - 频控:同 account 60s 内 1 条、当日 ≤10 条 → `10004`;同 IP 每小时 ≤20 条;
- 响应:`{ "code": 0, "data": { "cooldown": 60 } }`。

### 3.3 账密登录 `POST /auth/login`(公开)

```json
{ "account": "user@example.com 或 13800000000 或 用户名", "password": "..." }
```

- 服务端自动识别 account 类型(含 `@` → 邮箱;11 位数字 → 手机;否则用户名);
- 失败统一 `10001`,不区分账号不存在/密码错误;
- 同账号连续失败 5 次锁 10 分钟 → `10002`(Redis 计数,登录成功清零);
- 成功响应:

```json
{
  "code": 0,
  "data": {
    "access_token": "<jwt>",
    "expires_in": 7200,
    "user": { "id": "uuid", "username": "韩凯润", "avatar_url": null, "has_password": true }
  }
}
```

(refresh_token 通过 Set-Cookie 下发。)

### 3.4 验证码登录 `POST /auth/login-by-code`(公开)

```json
{ "account": "user@example.com", "code": "123456" }
```

- 校验失败(错误/过期/作废)→ `10005`;同 code 错误 5 次作废;
- account 未注册 → **自动注册**:username 取邮箱 @ 前缀或手机掩码(如 `138****0000`,冲突时追加随机后缀),然后按登录成功返回,额外带 `"is_new_user": true`,前端据此进入完善资料引导。

### 3.5 注册 `POST /auth/register`(公开)

```json
{ "username": "韩凯润", "account": "user@example.com", "code": "123456", "agreed": true }
```

- 校验:username 2–20 字符(中文/英文/数字/下划线)、唯一 → `10006`;account 未注册 → `10003`;验证码同 3.4;`agreed` 必须为 true(用户协议);
- 成功后自动登录,响应同 3.3 且 `is_new_user: true`。

### 3.6 重置密码 `POST /auth/reset-password`(公开)

```json
{ "username": "韩凯润", "account": "user@example.com", "code": "123456", "new_password": "..." }
```

- username 与 account 必须属于同一用户,否则统一 `10007`(不区分哪个错);
- 密码规则:8–64 位,同时含字母与数字 → `10008`;不得与近 3 次相同 → `10009`;
- 成功:更新 password_hash、追加 password_history、吊销该用户全部 refresh_token;响应 `{ "code": 0 }`。

### 3.7 刷新 / 登出 / 当前用户

| 接口 | 说明 |
| --- | --- |
| `POST /auth/refresh`(Cookie) | 轮换 token 对;旧 refresh 重用 → 吊销全部并返回 401 |
| `POST /auth/logout` | 吊销当前 refresh_token,清 Cookie |
| `GET /users/me` | 返回当前用户基本信息 + profile + 通知偏好(前端进入应用时拉取一次) |

### 3.8 资料与账号

| 接口 | 说明 |
| --- | --- |
| `PATCH /users/me/profile` | 更新简介:`{ avatar_url?, achievements?, bio? }`,服务端按 §2.3 约束校验 |
| `PATCH /users/me/username` | `{ "username": "..." }`;30 天内重复修改 → `10010` |
| `POST /users/me/change-account` | `{ "new_account": "...", "code": "..." }`(scene=`change_account`);更换绑定邮箱/手机 |
| `PUT /users/me/password` | `{ "code": "...", "new_password": "..." }`(验证码发至当前绑定账号);未设密码用户同接口设置 |
| `POST /users/me/oauth/{provider}/link` | 返回 302 跳转第三方授权;回调 `GET /users/me/oauth/{provider}/callback` 完成绑定;已绑他人 → `10011` |
| `DELETE /users/me/oauth/{provider}` | 解除关联;校验剩余登录方式 ≥1,否则 `10012` |
| `PUT /users/me/notification-preferences` | `{ "activity": true, "subscription": false, ... }` 整体覆盖写 |

### 3.9 头像/证件照上传

`POST /uploads/avatar`(multipart,字段名 `file`):
- JPG/PNG,≤5MB,服务端转 3:4 裁剪 + 压缩(最长边 1200px),存对象存储;
- 响应 `{ "url": "https://cdn.../avatars/uuid.jpg" }`,再随 `PATCH /users/me/profile` 提交。

## 4. 安全实现规范

1. 密码:bcrypt(cost ≥ 10);任何日志、错误响应不得含明文密码/验证码;
2. 验证码:生成用 CSPRNG,存哈希;发送走异步队列,接口不等待第三方回执;
3. 防爆破/防枚举:见各接口频控;`reset-password`、`register` 对存在性差异做恒定时间响应(不存在的账号也走完整校验流程再返回);
4. 限流(Redis 令牌桶):登录类接口同 IP 30 次/小时;验证码同 IP 20 条/小时;
5. CORS 白名单仅平台域名;Cookie 属性见 §1.1;
6. 审计:登录成功/失败、改密、换绑、OAuth 关联/解除写审计日志(user_id, ip, ua, at),保留 180 天。

## 5. 前端对接说明(本仓库改动点)

### 5.1 `stores/auth.ts`(当前为演示)

替换为:

```ts
interface AuthState {
  user: { id: string; username: string; avatarUrl: string | null } | null;
  status: "idle" | "loading" | "authed" | "guest";
  loginByPassword(account: string, password: string): Promise<void>;
  loginByCode(account: string, code: string): Promise<void>;
  register(...): Promise<void>;
  logout(): Promise<void>;
  refresh(): Promise<boolean>;
}
```

- access_token 存内存(zustand),不落 localStorage;页面加载时先 `refresh()` 恢复会话,再 `GET /users/me`;
- 用户卡片头像占位取 `user.username.slice(0, 1)`,与原型一致。

### 5.2 表单

- 登录弹窗三个 Tab、`/reset-password` 页:接入 react-hook-form + zod(依赖已装),schema 放 `lib/validations.ts` 与接口规则同源;
- 验证码按钮 60s 倒计时组件复用(响应里的 `cooldown` 驱动);
- 按钮 loading 态禁用,错误文案用接口返回的 `message`。

### 5.3 请求层

- 新建 `lib/api.ts`:统一 fetch 封装,自动带 token、401 时单飞 refresh 重放一次、业务码非 0 抛 `ApiError`;
- React Query 已就位(`providers/query-provider.tsx`),用户资料类查询 key 以 `["me", ...]` 前缀,登录/登出时 `queryClient.invalidateQueries(["me"])`。

### 5.4 外观偏好同步(已实现的本地逻辑保留)

- `stores/theme.ts`(localStorage 键 `shenzhi-theme`)继续作为**立即生效层**;登录后若服务端 `theme` 与本地不同,以服务端为准并写回本地;切换时同步 `PATCH /users/me/profile`;
- 未登录:仅本地。语言同理(新增 `stores/locale.ts` 或直接挂 profile)。

### 5.5 登录拦截

- 封装 `requireAuth(action)`:未登录 → 打开登录弹窗,登录成功后执行 `action`(收藏/关注等自动完成,见 PRD §3.5);
- 登录弹窗的打开/关闭提升为全局 UI store,任何组件可触发。

## 6. 业务错误码(1xxxx)

| code | 场景 | 用户文案 |
| --- | --- | --- |
| 10001 | 账号或密码错误 | 账号或密码不正确 |
| 10002 | 账号锁定 | 尝试次数过多,账号已锁定,请 10 分钟后再试 |
| 10003 | 账号已注册 | 该账号已注册,可直接登录 |
| 10004 | 验证码发送过频 | 发送太频繁,请稍后再试 |
| 10005 | 验证码错误/过期 | 验证码不正确或已过期,请重新获取 |
| 10006 | 用户名已存在 | 该用户名已被使用,换一个试试 |
| 10007 | 用户名与账号不匹配 | 用户名与账号不匹配 |
| 10008 | 密码不合规 | 密码需 8–64 位,且同时包含字母和数字 |
| 10009 | 密码与近期重复 | 新密码不能与最近使用的密码相同 |
| 10010 | 用户名修改过频 | 用户名 30 天内只能修改一次 |
| 10011 | 第三方账号已被绑定 | 该第三方账号已关联其他用户 |
| 10012 | 唯一登录方式 | 请至少保留一种登录方式 |

## 7. 测试要点

- 单测:验证码生成/校验/频控/作废;密码规则与历史校验;token 轮换与重用检测;
- 集成:注册→登录→refresh→登出→旧 token 失效全链路;重置密码后旧会话失效;
- 安全用例:账号枚举时间差、验证码爆破(错误 5 次)、限流触发;
- 前端:未登录点击收藏的「弹窗→登录→自动完成原操作」闭环;水合期头像闪烁检查(登录态在客户端恢复,骨架占位)。
